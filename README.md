# dsh-workbuddy-daily · WorkBuddy 每日积分领取

DSH 启动时**在后台**自动领取 WorkBuddy 各项积分，**已经做过就跳过，不重复请求**。

---

## 它领哪些积分

一共四类，都是**领取已经属于你的东西**，不伪造任何行为：

| 来源 | 做什么 | 典型收益 |
|---|---|---|
| **每日签到** | 今天没签就签到 | 100/天 |
| **猫猫旅行** | 到达了就收取；闲置就派出去 | 每次 6 左右 |
| **连登档位** | 解锁的档位自动兑换 + 抽奖 | 7d/14d/28d 档，50~150 |
| **成长任务** | 已达标的奖励自动领取 | 100 一次 |

外加两类**不发积分但会跑**的：

- **活跃上报**：让成长中心认为账号还在用（有些任务以此为前置条件）
- **服务补偿**：服务中断时才有，平时 0

> 任务中**需要你真实操作**的（关注公众号、用某个专家对话等），插件只负责"达标后自动领"，
> 不会替你去刷。原因见文末「诚实的边界」。

---

## 「已完成就不跑」是怎么保证的

一次启动按顺序跑，每步都是"先读状态，够了才写"：

**第一层：问上游。​** 签到先查 `today_checked_in`，已是 `true` 就**不发任何领取请求**。
旅行先查 `state`，只有 `arrived` 才收、`idle` 才派。
连登先查每个档位的 `tier_<name>_status`，`locked`/`claimed` 一律跳过。

**第二层：本地状态。​** 记录当天日期与已领任务码，同一天再启动**连任务列表都不拉**。

实测两次启动的差别（真实账号）：

| | 上游请求 | 说明 |
|---|---|---|
| 第 1 次启动 | 4~5 次 | 签到 + 旅行 + 连登 + 抽奖状态（+ 首次拉任务列表） |
| 第 2 次启动 | 4 次 | 全是**只读**状态查询，任务列表跳过 |

关键在于：**已完成的当天，之后每次启动只有只读请求，没有任何写操作。**

第三重保险：所有领取接口本身**幂等**。重复领取上游回 `already_claimed` + 0 积分，
插件当成功处理。即使状态文件被删也能安全重试。

---

## 为什么只读 `dsh-connect-workbuddy` 的凭证

插件**不做登录、不刷新 token、不轮换 refresh token**，只从
`~/.dsh/workbuddy-vault/<region>/` 读已存在的凭证。

这是刻意的：两个插件同时刷新同一个 refresh token 会互相作废，把你登出。
重复实现认证在这里是缺陷，不是特性。

没登录时插件**静默不做任何事**——不报错、不弹窗，这是正常状态而非故障。

## 已验证的事实（都是实测，不是推测）

| 事实 | 证据 |
|---|---|
| 签到状态接口是 **POST**（不是 GET），空 JSON body | 实测 200，`code: 0` |
| 签到成功立刻反映在状态里 | 领取后 `today_checked_in` 变 `true`，连签 25→26 |
| **签到积分确实进余额** | 净变化 +58.48 = +100 签到 − 41.52 消耗（消耗只可能让余额减少） |
| 旅行端点在 `/activity/growth/buddy/*`，**不在** `/v2` | `/v2/buddy/*` 一律 404，差点误判为"功能不存在" |
| 旅行收取需要 `record_id` | 状态里读到 `record_id: 33149589`，缺了上游拒绝 |
| **连登档位状态不在 tiers 数组里** | 在父对象 `tier_7d_status` 等字段；读错会每次产生 3 个被拒请求 |
| 连登兑换需要 `client_token`（UUID） | 上游按它去重 |
| 判断任务"已领取"的字段是 `accept_status`，**没有** `claimed` 字段 | 19 个任务里没有任何 `claimed`/`is_claimed` |
| 领任务奖励在 **web 域**，需 `Origin`/`Referer` + `x-client-platform: web` | 参考实现与实测一致 |
| 凭证在 `~/.dsh/workbuddy-vault/cn/*.json`，`auth.accessToken` | 实测读到 1331 字符 token |

### 两次真实的领取记录

```
=== 签到 ===
before: today_checked_in=false | streak=25 | today_credit=100
claim : http 200  {"credit":100,"streak_days":26}
after : today_checked_in=true  | streak=26

=== 猫猫旅行（古镇客栈） ===
before: state=arrived | record_id=33149589 | reward_credit=6
claim : +6 credits
after : 余额 +2.75（6 分减去本轮对话消耗）
```

## 设置项

| 设置 | 默认 | 说明 |
|---|---|---|
| `enabled` | true | 总开关，关掉插件完全不动 |
| `checkinEnabled` | true | 每日签到 |
| `travelEnabled` | true | 猫猫旅行（出发 / 收取） |
| `streakEnabled` | true | 连登档位兑换 + 抽奖 |
| `tasksEnabled` | true | 成长任务扫描 |
| `claimAllReady` | true | 关掉则只报告不领 |
| `region` | `cn` | `cn` 国内版 / `global` 国际版 |
| `startDelaySeconds` | 8 | 启动后等多久再联网，保证不拖慢 DSH |

## 路由

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/plugins/dsh-workbuddy-daily/status` | 上次执行结果、今天是否跑过、下次启动会做什么 |
| POST | `/plugins/dsh-workbuddy-daily/run` | 立即手动跑一次（202，后台执行） |

均经过 loopback + 同源校验——这些路由能触发对真实账号的写操作。

## 状态文件

`~/.dsh/.workbuddy-daily/daily.json`，原子写入（临时文件 + rename），
不会因为写了一半而卡在"永不执行"。

```json
{
  "day": "2026-10-30",
  "region": "cn",
  "summary": "claimed",
  "claimedTaskCodes": [],
  "actions": [{ "step": "travel", "credit": 6, "locationName": "古镇客栈" }]
}
```

删掉它只会让插件下次重新扫一遍任务（上游幂等保护，不会重复发奖）。

| 测试 | 覆盖 | 结果 |
|---|---|---|
| `node --check` | 两个半部 | 通过 |
| 行为测试 | 签到 / 任务 / **已完成后跳过** / 状态隔离 / 幂等 / 未登录 / 上游失败 / 禁用 | **19/19** |

关键断言是**按请求数与请求方法**判断的，而不是只看最终状态——
因为需求本质是"不要再发写请求"，只看状态的话，即使每次启动都调用领取接口也会通过。

## 诚实的边界

- **不代替你做任务。​** 关注公众号、发帖、用某个专家对话这类需要真实行为的任务，
  插件只领你**已达标的**奖励，不伪造使用记录。伪造事件（向 `/v2/report` 上报假的
  点击/浏览/"用过专家"）确实能让任务达标，但那是向平台提供不实记录，可能违反服务条款
  并危及账号，所以没有实现。
- **依赖已登录账号。​** 没登录时它什么也不做。凭证过期需 `dsh-connect-workbuddy` 刷新。
- **猫猫旅行一次只推进一步。​** 派出去后要等 4 小时才回来，下次启动才收得到。
- **上游规则可能变。​** 端点或字段变了，插件记录错误并继续正常启动，不会让 DSH 起不来。
- **`accept_status` 可能有延迟。​** 这就是本地状态存在的价值：即使上游晚一步反映，
  同一天也不会重复请求。
